# 需求、证据与实现边界

> 草案｜2026-10-28｜用户要求先交完整设计，再开展功能开发。

## 1. 对需求的理解

这次交付是一套 Anka 设备接入能力，以及它的第一个游戏手柄应用。
手机通过新网页变成手柄；ESP-Mosaico 运行专用手柄应用；两者通过 WebSocket
向 Anka 接入。设备授权绑定已有玩家，输入最终驱动该玩家游戏运行实例。

| 用户要求 | 对应设计 |
|---|---|
| 类似 Switch 的自制手柄体验 | 双主键、体感微调、触控操作、配对状态与触觉反馈 |
| ESP-Mosaico 和手机，不限 iPhone | 同一动作模型，两种设备适配器，按实际能力协商 |
| 两个按键、中间小屏 | 实体双键 / 手机虚拟双键；中间为主要触控区 |
| 滑动选方向、中心圆跳、四角与四边八功能 | 九宫格位置保留；用手势识别区分滑动和点击 |
| WebSocket 接入，设备与玩家不同 | Device Hub、独立设备凭证与设备 WS，不占玩家席位 |
| 新增手柄设备接入按钮，控制当前玩家 | 从当前游戏接收端创建配对，服务器推导玩家与实例 |
| 扫二维码 | bindKey+短期token直接WSS绑定；ESP启动手柄应用后扫码 |
| 陀螺仪改变视觉朝向 | 相对体感瞄准、坐标归一化、校准、离合、滤波与触控兜底 |
| User、邀请 Share、Device 是三套鉴权 | 三套凭证、验证入口、存储命名空间与权限边界 |
| 一个玩家本期只接入一种设备 | 一人一台、手机或 ESP 二选一；解绑后才能更换 |
| 资料放到 anka doc/mosaico | 本目录保存索引、官方材料、版本校验与设计记录 |

默认将「滑动方向」解释为视角相对的平面移动；观察方向由陀螺仪控制。
这里的双键指扩展板两颗操作键，不占用主板 Power / BOOT 作为射击键。
八个功能的具体分配是本方案建议，后续可在布局配置中调整。

## 2. 已核实的硬件事实

| 项目 | 官方资料结论 | 设计影响 |
|---|---|---|
| 主芯片 | ESP32-S31，目标 `esp32s31` | 不使用 ESP32-S3 目标或随意替换 IDF |
| 屏幕 | 2.16 英寸、480×480、CO5300 QSPI AMOLED | 实体 UI 使用固定逻辑坐标，自适配手机 |
| IMU | BMI270 六轴加速度计 + 陀螺仪 | 能做体感瞄准，需偏置校准和姿态融合 |
| 磁传感器 | 两颗 BMM150，用于磁吸交互等 | 不默认当作可靠世界航向；磁吸结构易干扰 |
| 主板反馈 | 振动马达；v1.0 与 v1.2 状态灯存在差异 | 按板版本探测，不硬编码可用灯 |
| 交互扩展板 | 两路按键/电容触摸，六颗 WS2812 | 顶部四灯 + 两颗按键灯，与用户图一致 |
| 摄像头 | 单独扩展模块，仅左侧槽 | 主板不能被假定自带扫码摄像头 |
| 板版本 | BSP 支持 v1.0 / v1.2，部分引脚不同 | 使用 BSP 高层接口和板版本识别 |
| 电池 | 主板文档列 3.7V / 65mAh 小电池 | 高频 Wi-Fi、亮屏、灯和马达必须实测续航 |

证据：[主板指南](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32s31/esp-mosaico/user_guide.html)、
[交互模块指南](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32s31/esp-mosaico/user_guide_interact.html)、
[官方 BSP](https://github.com/esp-mosaico/esp-mosaico-bsp)。本地副本见 [资料索引](../SOURCES.md)。

存在一处需保留的资料差异：主板指南写 CST9220 系列触控，BSP README 写 CST9217。
实现以实际板型、BSP 驱动与读回数据为准；不能据此承诺多点触控。
屏幕驱动可接收多个触点不代表应用框架已暴露多个独立触点。

## 3. 已核实的 Anka 现状

| 现有文件（Anka 根目录相对路径） | 当前能力 | 新功能接入方式 |
|---|---|---|
| `server/app/auth.py` | User 的 `anka_session` HMAC 会话 | 保留其账号身份语义，显式授权设备绑定 |
| `server/app/rooms/security.py` | User / Share 房间访问判定 | 增加只对本人有效的设备绑定授权适配器 |
| `server/app/rooms/store.py` | Share 邀请和访客能力存储 | 借鉴能力隔离，本期设备配对/绑定用独立内存状态 |
| `server/app/rooms/transport.py` | 大厅与战斗消息、有界队列、角色权限 | 玩家联机保持原协议，设备另建 WS |
| `server/app/main.py` | HTTP 保护、明确放行入口、路由挂载 | 只增加薄挂载和独立设备入口，不装业务逻辑 |
| `web/vite.config.ts` | 开发代理、PWA 资源策略 | 加设备页/WS 代理与 SW 排除规则 |
| `plugins/anka-outpost-strike/server/main.py` | 通过 `fiber.effect` 注册房间定义 | 同样注册设备游戏适配器，卸载撤销绑定 |
| `plugins/anka-outpost-strike/game/engine.js` | `keys`、`touchMove`、`heldFire`、动作方法 | 增加 InputRouter，统一输入，不伪造 DOM 键盘事件 |
| `plugins/anka-outpost-strike/game/perspective.js` | `lookYaw` / `lookPitch`，第一/第三人称 | 统一体感增量与现有相机约束 |
| `plugins/anka-outpost-strike/game/App.vue` | 游戏生命周期、触控和联机协调 | 挂接本人设备输入、配对弹层、前台状态 |
| `plugins/anka-outpost-strike/game/online-hooks.js` | 开火/治疗/补给等进入现有联机动作 | 设备只产生输入，不绕过伤害/弹药权威 |
| `plugins/anka-outpost-strike/game/network.js` | 房间玩家本地身份和联机 | 不让手柄创建 GameNetwork 或加入房间 |

源代码确认：现有移动以视角 yaw 为基准，支持平面模拟量；现有俯仰角随第一/第三人称变化。
现有联机暂停只释放本地输入并提示「联机比赛继续进行」，设备断线应遵循相同规则。
已有 qrcode 依赖可用于游戏端二维码，手机手柄页单独构建轻量产物。

## 4. 范围边界

本期完整范围包含：设备服务、三套鉴权边界、单人/房主/Share 当前玩家绑定、
手机独立页面、ESP 专用应用、扫码自动绑定、九宫格与双键、体感、双向反馈、
安全断线、重连、输入接管、固定/v1协议和真机验收。

未来扩展保留版本化路径/v1和独立Device服务，暂不做profile/capabilities协商。
ESP无摄像头的反向扫码留作后续可选，不增加本期activation/polling流程。
本期不实现多设备并发、左右分体、设备待命列表、输入通道组合或无缝热切换。

本期不更换游戏网络权威、不承诺浏览器全部机型有陀螺仪/振动、不采用蓝牙 HID 替代 WS。
可提供触控观察作为无 IMU 设备的完整可玩路径；有硬件能力的 iOS/Android 必须真机验收。

## 5. 需开发阶段实测的事项

- 用户手中的主板版本、扩展板按键接线/模式与左右安装方向。
- CST 触点数、框架触点暴露、拖动与独立按钮并发是否满足组合操作。
- 摄像头存在与型号；扫码解码器内存、帧率与强反光屏幕识读率。
- BMI270 轴向、温漂、噪声，马达震动时的体感污染。
- 手机权限、浏览器传感器采样、横竖屏、微信等内嵌浏览器的能力。
- 公网部署位置、Wi-Fi 干扰和游戏帧率导致的实际端到端延迟。

这些是可验证的工程条件，不影响先完成协议和交互设计；验收必须分别报告通过、降级和未测。
